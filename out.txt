ABSTRACT 
The Driving and Vehicle License Department (DVLD) Management System is developed to 
modernize and automate the traditionally manual driving license administration process. In many 
regions, including Ethiopia, licensing services rely heavily on paper -based procedures, physical 
visits, and fragmented record management, which result in long processing times, data 
inconsistency, limited transparency, and high operational workload. These challenges negatively 
affect applicants, driving schools, and DVLD administ rative staff, creating a strong need for a 
centralized and efficient digital solution. 
This project proposes a secure, scalable, and integrated DVLD Management System that connects 
applicants, driving schools, and DVLD authorities through a unified digital platform. The system 
provides a mobile application for applicants and a desktop -based application for driving schools 
and DVLD staff, enabling online registration, application tracking, document management, 
automated scheduling, and notification services. Developed using a three -tier architecture and 
modern technologies such as C#, .NET, Flutter, and SQL Server, the system ensures data security 
through Role-Based Access Control (RBAC) and centralized database management. The proposed 
solution enhances efficiency, reduces manual errors, improves service transparency, and supports 
future expansion toward comprehensive e-government services.

 Chapter 1: Introduction 
1.1. Introduction 
The Driving and Vehicle License Department (DVLD) Management System is intended to 
streamline and computerize the formerly manual processes of driving license issuances, driving 
schools and communication with the applicants.  The project unveils a more centralized and 
organized digital platform bringing together an administrative system based on desktops and 
mobile access by the applicants. 
The system allows applicants to apply, monitor application status, and get notifications as well as 
handle license-related services through a mobile -based application. A desktop based system is 
used by driving schools and DVLD staff to run through registrations, training schedules, 
examination and issuing of licenses.  The system provides adequate coordination between the 
applicants, driving institutes, as well as the DVLD, by ensuring the existence of a centralized 
database and a standardized workflow. 
The DVLD Management System enhances efficiency, transparency, and service delivery by 
automating scheduling and notifications and reducing manual paperwork and imposing structured 
business rules. The project helps to continue enhancing the digital transformation processes in the 
administration and maintain the security of the work as it offers a scalable, secure and user-friendly 
solution to address driving license operations. 
1.2. Background of the Project 
In most areas, driving license administration remains in the manual systems by use of physical 
documents, physical application and disjointed record storage systems across multiple offices and 
driving schools. This has a tendency of making applicants wait a lot, visit several times and have 
less visibility of the progress of the applications.  Driving schools also have independent records 
that are not always aligned with the DVLD which increases the risk of errors and data 
inconsistency. 2 
 
As e-government projects expanded and more people started to use mobile technologies, it became 
necessary to have a single chain that may link applicants, driving schools and the DVLD into a 
single digital space. The suggested DVLD Management System provides solutions to these issues 
by proposing the idea of mobile -based communication with the applicants, desktop -based 
administrative control, centralized information management, and automated communication 
systems. 
The system substitutes the separated, paper -based processes with the organized computer 
processes including electronic application processing, planned tests, training status monitoring, 
and license management.  This will enhance better coordination between stakeholders and also 
guarantee long term scalability and accuracy of data. 
1.3. Statement of the Problem 
Existing systems suffer from:  
● Manual verification and data entry leading to long processing times  
● No unified platform connecting applicants, driving schools, and the DVLD 
● Lack of automated notifications and scheduling systems  
● Difficulty tracking application status across different offices  
● Lack of centralized digital records shared across institutions  
● Fragmented and inconsistent record management 
● Limited transparency for applicants during the licensing process  
● Limited scalability for future nationwide expansion  
There is a strong need for an automated system that:  
● Integrates applicants, driving schools, and the DVLD into a single platform 
● Supports mobile access for applicants and desktop dashboards for administrators 
● Automates application tracking, scheduling, and notifications 
● Ensures reliable and centralized data storage 
● Improves operational efficiency and service transparency 
● Allows future extensibility for additional digital services 3 
 
1.4. Objective of the Project 
1.4.1. General Objectives 
To design and develop a secure, scalable, and fully automated Driving and Vehicle License 
Department (DVLD) Management System that streamlines and modernizes the entire licensing 
process. The system will enhance coordination and communication among applica nts, driving 
schools, and the DVLD by providing an integrated platform accessible through both mobile and 
desktop applications. It will ensure data security, support high user volumes, and automate key 
workflows such as application submission, scheduling o f driving tests, issuance of licenses, and 
renewal processes. By leveraging modern technologies, the platform will reduce manual errors, 
minimize processing time, and improve transparency. Additionally, it will offer real-time tracking 
of application status, digital notifications, and centralized record management, thereby fostering 
efficiency, accountability, and user satisfaction across all stakeholders involved in the licensing 
ecosystem. 
1.4.2. Specific Objectives 
● Develop a centralized database to securely store applicant, school, exam, and license 
records for easy access and consistency. 
● Enable mobile registration so applicants can sign up with driving schools directly through 
a user-friendly app. 
● Provide a desktop dashboard for schools to manage trainees, schedules, and progress with 
simple reporting tools. 
● Support the management and recording of theory and practical test results within the

● Automate test scheduling and application status updates to reduce manual coordination.

Chapter 2: Description of Existing System and Literature Review  
2.1. Major Function of Existing System 
The current driving license management process in Ethiopia is largely manual, paper based, and 
dependent on physical interactions between applicants and DVLD offices. Although some offices 
have introduced partial computerization , the majority of core operations still rely on human driven 
procedures. The existing system performs several major functions ,but each function is executed 
through traditional work flows that lack automation, centralized data access , or real time 
communication.   
 Applicant Registration and Document Collection 
Applicants must physically visit the DVLD office to submit registration forms and provide 
supporting documents such as ID cards, previous license levels, medical certificates, and 
payment receipts. The staff manually check these documents and record applic ant details 
in logbooks or basic computer files. 
Input: Paper forms, applicant documents 
Process: Manual verification and data entry 
Output: Paper-based applicant file 
I. Written, Vision, and Practical Test Scheduling 
The scheduling of vision tests, written exams, and street driving tests is handled manually 
by staff. Applicants are assigned examination dates based on availability, often recorded 
in notebooks or Excel sheets. Applicants must return or call to confirm their exam dates. 
Input: Applicant information and preferred exam dates 
Process: Staff manually assign test slots 
Output: Handwritten or verbally communicated test schedules 
II. Conducting Tests and Recording Results 11 
 
Test results are recorded by evaluators on printed score sheets during the assessment 
process. These sheets are then collected and submitted to administrative personnel, who 
are responsible for manually entering the data into local files or official registers. Because 
this process relies heavily on manual transcription, errors can occasionally occur when 
transferring information. When such mistakes are identified, corrections must be handled 
through a separate procedure, which not only increases the workloa d but also introduces 
delays in finalizing and validating the records 
Input: Test score sheets 
Process: Manual scoring and manual entry 
Output: Paper records and occasional scattered digital files 
III. License Issuance and Renewal 
Once an applicant passes the required tests, their information is manually processed to issue 
a new license or renew an existing one. Staff prepare physical license cards, often relying 
on basic printing tools without centralized validation across regions. 
Input: Approved applicant records 
Process: Manual license card preparation 
Output: Physical driving license 
IV. Handling Complaints and Communication 
Communication between applicants and staff occurs mainly through in -person visits, 
phone calls, or notice boards. There is no automated notification system for exam 
reminders, document updates, or result announcements. 
Input: Applicant complaints and inquiries 
Process: Staff response via face-to-face or phone communication 
Output: Informal issue handling and resolutions 
V. Record Keeping and Reporting 12 
 
DVLD offices maintain large volumes of physical files and scattered digital documents. 
Generating reports for performance analysis, fraud investigation, or policy evaluation 
requires extensive manual effort, and often the data is incomplete or inconsistent. 
Input: Paper files, Excel sheets, local computer records 
Process: Manual sorting and compilation 
Output: Delayed and sometimes inaccurate reports 
2.2. Users of the Current System 
The existing driving license management process serves multiple stakeholders who directly 
interact with the system for various purposes. These users depend on the current manual 
procedures to perform tasks such as registration, verification, testing, licen se issuance, and 
administrative management. The needs and expectations of these users vary based on their roles, 
but most require faster processing, transparency, and reliable communication. 
Below are the primary users of the current system:  
I. Applicants (New and Renewal Candidates) 
Applicants include individuals seeking a new driving license, upgrading their license level, 
or renewing an existing license. They form the largest user group of the system. 
Needs and expectations: 
● Simple and clear registration process 
● Accurate information about test dates 
● Quick results and feedback 
● Reduced waiting times and queues 
● Reliable communication about requirements, exam schedules, and status updates 
● Transparent procedures with minimal manual errors 
II. DVLD Administrative Staff 
These employees are responsible for handling key administrative tasks such as applicant 
registration, document verification, accurate data entry, card printing, and maintaining 13 
 
applicant records. They perform most of the manual work required in the current system, 
ensuring that essential processes are completed efficiently. 
Needs and expectations: 
● Streamlined workflows to reduce workload 
● Centralized applicant records for easy access 
● Tools to minimize repetitive manual tasks 
● Faster verification methods 
● Reduced risk of errors during data entry 
● improved accuracy and reduced paperwork 
III. Management and Supervisors (DVLD Officials) 
Higher-level officials are tasked with overseeing the overall operations of the system, 
ensuring that processes run smoothly and efficiently. Their responsibilities include 
preparing detailed reports, making key administrative and strategic decisions, and 
monitoring adherence to national driving regulations. By fulfilling these duties, they play 
an essential role in maintaining accountability, providing direction, and guiding the system 
toward consistent and effective performance 
Needs and expectations: 
● Accurate and up-to-date reports 
● Reliable record-keeping for auditing and monitoring 
● Tools to detect fraud or duplication 
● Insights for planning and resource allocation 
2.3.  Drawbacks of the Current System 
The existing driving license management system in Ethiopia relies heavily on manual procedures, 
paper-based documentation, and fragmented digital tools. While it fulfills basic operational needs, 
it suffers from numerous drawbacks that limit efficiency, ac curacy, transparency, and scalability. 14 
 
These limitations directly affect applicants, DVLD staff, and other stakeholders who depend on 
reliable and timely services. 
The major drawbacks of the current system include: 
I. Inefficiency and Slow Processing 
Most procedures including registration, test scheduling, verification, and license issuance 
are performed manually.  
This leads to: 
● Long queues and extended waiting times 
● Delays in examination and result processing 
● Difficulty handling large numbers of applicants 
● Repetitive tasks that increase staff workload 
II. High Risk of Errors and Inaccuracy 
Manual data entry and paper-based record handling increase the chances of: 
● Typographical mistakes 
● Misplaced or incomplete files 
● Incorrect exam results due to transcription errors 
● Duplicate or conflicting records 
III. Lack of Centralized Data Management 
Different DVLD branches maintain their own local files, spreadsheets, or handwritten 
logbooks to record and track applicant information. Because each branch relies on separate 
systems, this fragmented approach often leads to duplication, inconsistencies, a nd 
difficulties in consolidating records across the organization. This creates issues such as: 
● Inconsistent records across regions 
● Difficulty tracking applicants who register in multiple branches 
● Limited ability to detect duplicate or fraudulent licenses 
● Poor sharing of information between offices 15 
 
IV. Limited Communication and No Notification System 
Applicants receive updates manually through: 
● Physical visits 
● Phone calls 
● Notice boards 
            This communication method causes: 
● Missed exam dates 
● Lack of reminders for document submission 
● Poor applicant-staff interaction 
● Increased confusion and repeated office visits 
V. Inadequate Fraud Prevention

2.4. Literature Review 
A literature review examines existing studies, theories, and systems relevant to the development 
of a Driving License Management System. It highlights previous efforts in digitalizing licensing 
processes, explores technological frameworks applied in similar projects, and identifies gaps that 
this project aims to address. This review is organized into thematic areas that reflect major 17 
 
components of the system: e -government digitalization, license management systems, database -
driven public services, AI-based automation, and software engineering methodologies. 
I.  E-Government and Digital Public Service Delivery 
Globally, governments have been transitioning from manual administrative processes to 
automated digital platforms. According to studies on e -government systems, digitalization 
improves transparency, reduces corruption, and enhances service delivery efficie ncy 
(Sommerville, 2020). Research indicates that public institutions adopting electronic systems 
benefit from reduced bureaucracy, faster communication, and better accountability due to 
centralized data handling (Pressman, 2020). 
In developing countries, including Ethiopia, the shift toward electronic public services remains a 
priority. Literature emphasizes that digitized platforms significantly minimize the challenges 
associated with paper -based systems, such as data loss, long q ueues, and inconsistent service 
quality. This creates an enabling context for developing an intelligent DVLD system that aligns 
with national digital transformation goals. 
II. Driving License Management Systems in Other Countries 
Several countries have implemented automated driving license systems that replace manual 
registration and verification. For example, India and Kenya have adopted digital license issuance 
systems integrated with centralized government databases, reducing fr aud and enabling online 
verification. Similarly, Rwanda and Ghana use e -license platforms that allow applicants to 
schedule tests, submit documents, and receive updates through mobile interfaces. Studies of these 
systems show that automation leads to measu rable improvements in accuracy, workflow 
efficiency, and record management. However, many African nations still face limitations in 
scalability, offline support, cross -platform access, and AI integration. This suggests a gap in 
standard license systems tha t your project aims to fill by combining desktop, mobile, and 
intelligent functionalities. 
III. Role of Databases in Public Administration 18 
 
Literature on database systems emphasizes the importance of centralized data for ensuring data 
consistency, accuracy, and secure access (Microsoft SQL Server Documentation, 2025). In 
traditional government processes, decentralized data storage leads to dup lication, inconsistency, 
and difficulty in auditing. Research highlights that structured database management systems 
(DBMS) enable: 
● Secure storage of citizen data 
● Reliable retrieval and updating 
● Prevention of unauthorized access 
● Support for generating analytical reports 
SQL-based systems are commonly used in government applications due to their robustness, 
scalability, and support for complex queries. These insights justify the adoption of SQL Server in 
this project to enhance the reliability and transparency of driving license records. 
IV. Digital Identity, Validation, and Fraud Prevention 
Research in digital identity systems highlights common challenges such as identity theft, duplicate 
registrations, and document forgery. Systems that rely heavily on manual verification often 
struggle to detect inconsistencies in applicant data. Studies re commend the use of automated 
biometric verification, document scanning, and machine learning to enhance integrity.While 
Ethiopia has implemented digital ID programs (Fayda ID), integration with DVLD systems 
remains limited. Literature suggests that linking  identity records with intelligent license 
management systems improves: 
● Verification accuracy 
● Data integrity 
● National record consistency 
V.  Identified Gaps in Existing Research and Systems 
The literature highlights several notable gaps in existing driving license management solutions: 
● Lack of combined desktop and mobile support  – Current systems often operate on a 
single platform, limiting accessibility and flexibility for both administrators and applicants. 19 
 
● Insufficient offline capabilities – In regions with poor or unstable internet connectivity, 
users face significant challenges, as most solutions rely heavily on continuous online 
access. 
● Limited integration between public service platforms  – Fragmented systems prevent 
seamless data sharing and coordination across government agencies, reducing efficiency 
and transparency. 
● Weak fraud detection mechanisms  – Reliance on manual checks makes it difficult to 
identify and prevent fraudulent activities, leaving the system vulnerable to misuse. 
● Limited user experience design – Interfaces are often not tailored to applicants with low 
digital literacy, creating barriers to access and increasing the likelihood of errors during 
application or renewal processes.

Chapter 3: Proposed System Documentation 
3.1 Overview 
The proposed Driving and Vehicle License Department (DVLD) Management System aims at 
integrating all key operations of licensing under the same digital platform. It links the applicants, 
the driving schools and the DVLD in a unison of mobile and desktop applications where all three 
parties are capable of accessing the services they require at ease. 
The aim of the system is to enhance the whole system of licensing that includes registration and 
document filing to the school approval, DVLD check, exam arrangement and issuing of the final 
license. It also aids in online theory tests, automatic reminders  to the exam sessions, and safe 
transfer of data between the driving schools and the main DVLD office. 
The system is technically constructed on three tiers (presentation layer, business logic layer, and 
data layer) and role -based access control. All the clients interact safely with a centralized SQL 
Server database which promotes consistency and easy synchr onization of data with mobile and 
desktop interfaces. 
3.2 Functional Requirements

group, as well as the shared services that support all operations.

● Provision supporting documentation through the Application Management Service for all

● Apply for an international driving license. 
● View license details, expiry dates, and status. 
● Access driving history and past test attempts. 
● View and download payment receipts. 
● Update profile information and re-upload documents if required.

● Consider applications provided by applicants and accept, reject or demand more

The non-functional requirements describe the overall qualities the system must maintain to ensure 
a smooth, reliable, and secure experience for all users.

The system should respond quickly to user actions, handle multiple applicants and schools working 
at the same time, and keep data processing such as scheduling or verification efficient even during

❖ Reliability 
All core services should work consistently without frequent interruptions or unexpected downtime. 
Data must remain intact and protected, avoiding loss or corruption. Critical operations like exam 
scheduling and document verification should run smoothly without failures. 
❖ Availability 
The system should remain accessible at all times, ensuring users can depend on its availability 
whenever needed. Driving schools and DVLD staff must be able to carry out their work without 
interruptions or downtime. Applicants should also have reliable acc ess to mobile services, 
allowing them to complete tasks smoothly at any time.

Sensitive data such as IDs, personal details, and exam records must be safeguarded at all times.

access mechanisms. Only authorized users should be permitted to view, update, or modify records, 
ensuring confidentiality and integrity 
❖ Usability 
All interfaces (mobile and desktop) should be simple to navigate, allowing users to complete tasks 
without confusion. Applicants should find the mobile app straightforward, while staff dashboards 
should support clear workflows. 
❖ Scalability 
The system should be designed to grow and expand over time, supporting an increasing number 
of users and driving schools as demand rises. It must also be capable of scaling toward wider 
national integration, ensuring smooth adoption across regions.This gro wth should be achieved

3.4. System model 
3.4.1 Scenarios 
Scenario 1: Applicant Registration 
● Initial Assumption: 
The applicant can register either remotely using the DVLD mobile application or in 
person at a DVLD office or affiliated driving school through the desktop system. 
● Normal Flow (Mobile Registration): 
The applicant opens the DVLD mobile application, enters personal information (full 
name, date of birth, phone number, address), uploads a national ID and photograph, and 24 
 
submits the registration form. If all data is valid, the system redirects the applicant to the 
verification page. 
● Alternative Flow (In-Person Registration via Desktop Application): 
A DVLD staff member or driving school officer registers the applicant using the desktop 
application by entering personal details and uploading required documents on behalf of 
the applicant. 
● What Can Go Wrong: 
Invalid phone number format, missing mandatory fields, duplicate records, or 
unsupported document formats. In such cases, the system displays an error message and 
requires correction. 
● System State on Completion: 
Applicant data is saved with an unverified or pending verification status, and a 
verification code or confirmation process is initiated. 
Scenario 2: Applicant Login 
● Initial Assumption: 
 The applicant is registered and verified in the system. 
● Normal Flow: 
 The applicant enters their phone number and password. If credentials are valid, the 
system authenticates the user and redirects them to the home dashboard. 
● What Can Go Wrong: 
 Invalid credentials or locked account. The system displays an appropriate error message. 
● System State on Completion: 
 A secure authenticated session is created for the applicant. 
Scenario 3: Selecting a Driving School and Submitting Application 
● Initial Assumption: 
 The applicant is logged into the system. 
● Normal Flow: 
 The applicant selects a preferred driving school from the available list, reviews school 25 
 
details, and submits a driving license application. Required documents are verified, and 
the application is forwarded to the selected school. 
● What Can Go Wrong: 
 Missing documents, invalid selections, or unavailable training slots. 
● System State on Completion: 
 The application is stored in the system and marked as Pending School Review. 
Scenario 4: Driving School Reviewing Applications 
● Initial Assumption: 
 A driving school administrator is authenticated using the desktop application. 
● Normal Flow: 
 The administrator reviews submitted applications, checks applicant details, and either 
approves, rejects, or requests additional documents. 
● What Can Go Wrong: 
 Incomplete school authorization, missing applicant data, or system interruptions. 
● System State on Completion: 
 Application status is updated, and the applicant is notified of the decision. 
Scenario 5: Training Schedule and Notifications 
● Initial Assumption: 
 The applicant has been accepted by a driving school. 
● Normal Flow: 
 The driving school administrator creates a training schedule and assigns instructors. The 
applicant receives notifications and can view training dates through the mobile 
application or via office communication. 
● What Can Go Wrong: 
 Schedule conflicts, unavailable instructors, or data synchronization issues. 
● System State on Completion: 
 Training schedule is stored and synchronized with the DVLD system. 
Scenario 6: Vision Test Scheduling and Evaluation (Local License) 26 
 
● Initial Assumption: 
 The applicant has completed training and is eligible for testing. 
● Normal Flow: 
 DVLD staff schedules a vision test through the desktop application. The applicant is 
notified of the schedule via the mobile app or in person. A vision test officer records the 
test result in the system. 
● What Can Go Wrong: 
 Applicant fails the vision test, misses the appointment, or medical requirements are not 
met. 
● System State on Completion: 
 Vision test results are stored. Passing the vision test is a prerequisite for the theory 
test. 
Scenario 7: Theory Test Scheduling and Attendance 
● Initial Assumption: 
 The applicant has passed the vision test. 
● Normal Flow: 
 DVLD staff schedules a theory exam using the desktop system. The applicant receives 
the exam details through notification. The applicant attends the exam as scheduled. 
● What Can Go Wrong: 
 Unavailable slots, applicant absence, or scheduling conflicts. If the vision test is not 
passed, theory scheduling is blocked. 
● System State on Completion: 
 Theory test attendance is recorded and awaits result entry. 
Scenario 8: Theory Test Result and Retake (If Required) 
● Initial Assumption: 
 The applicant has attended the theory test. 
● Normal Flow: 
 A DVLD test officer records the theory test result. If the applicant passes, they become 
eligible for the practical test. If failed, the applicant may request a retake. 27 
 
● What Can Go Wrong: 
 Applicant fails the test, exceeds retake limits, or has unpaid retake fees. 
● System State on Completion: 
 Applicant status updated to Theory Passed or Retake Required. 
 Passing the theory test is a prerequisite for the practical test. 
Scenario 9: Practical Test Scheduling 
● Initial Assumption: 
 The applicant has passed both the vision and theory tests. 
● Normal Flow: 
 DVLD staff assign a practical driving exam date using the desktop application. The 
applicant receives notification via the mobile app. 
● What Can Go Wrong: 
 No available examiners, incomplete records, or scheduling conflicts. 
● System State on Completion: 
 Practical test appointment stored and confirmed. 
Scenario 10: Practical Test Result and Retake (If Required) 
● Initial Assumption: 
 The applicant has attended the practical driving exam. 
● Normal Flow: 
 The examiner records the result in the system. If the applicant passes, they become 
eligible for license issuance. If failed, a retake can be requested. 
● What Can Go Wrong: 
 Applicant fails the test, examiner report missing, or misconduct during the exam. 
● System State on Completion: 
 Applicant status updated to Practical Passed or Retake Required. 
Scenario 11: Local Driving License Issuance 
● Initial Assumption: 
 The applicant has passed all required tests. 28 
 
● Normal Flow: 
 DVLD staff verifies the applicant’s records and issues a local driving license using the 
desktop system. The applicant is notified and can view license details through the mobile 
app. 
● What Can Go Wrong: 
 Outstanding fees, missing documents, or system processing errors. 
● System State on Completion: 
 License status updated to Issued and Active. 
Scenario 12: Driving License Renewal 
● Initial Assumption: 
 The applicant owns an active or expiring driving license. 
● Normal Flow: 
 The applicant submits a renewal request via the mobile app or in person. Required 
documents and medical reports are uploaded or verified. DVLD staff approves the 
request and updates the license validity. 
● What Can Go Wrong: 
 Expired license beyond renewal limits, invalid medical report, or unpaid fees. 
● System State on Completion: 
 License validity updated or renewal request rejected. 
Scenario 13: Lost or Damaged License Replacement 
● Initial Assumption: 
 The applicant owns a valid license that is lost or damaged. 
● Normal Flow: 
 The applicant submits a replacement request and pays the required fee. DVLD staff 
verifies the record and issues a replacement license. 
● What Can Go Wrong: 
 Incorrect license details, identity mismatch, or unpaid replacement fees. 
● System State on Completion: 
 Replacement license issued and old license marked invalid or inactive. 29 
 
Scenario 14: International Driving License Application 
● Initial Assumption: 
 The applicant holds a valid local driving license. 
● Normal Flow: 
 The applicant submits an international license request along with required documents 
and payment. DVLD staff reviews and approves the application. 
● What Can Go Wrong: 
 Expired local license, missing passport, or payment issues. 
● System State on Completion: 
 International license application saved with Approved or Pending status. 
Scenario 15: License Detainment and Release 
● Initial Assumption: 
 A traffic violation requiring license detainment has occurred. 
● Normal Flow: 
 Authorized personnel record the detainment in the system. After fine payment, the 
applicant requests release. DVLD staff verifies payment and restores the license. 
● What Can Go Wrong: 
 Incorrect violation data, unpaid fines, or record mismatch. 
● System State on Completion: 
 License status restored to Active.

lost/damaged, and international applications bypass the exam stages.

Chapter 4: System design  
4.1. Overview 
This section provides an overview of the system design for the proposed Driving License 
Management System (DVLD). The system is designed to support the complete lifecycle of driving 
license management, including application submission, mandatory training, testing, license 
issuance, renewal, and administrative control. 
The DVLD system adopts a layered and modular design, consisting of a presentation layer, 
business logic layer, and data layer. The presentation layer includes a single desktop application 
used by DVLD staff and driving institute personnel, as well as a mob ile application used by 
applicants. Access to system functionalities within the desktop application is controlled using role-
based access control (RBAC), ensuring that each user interacts only with the features relevant to 
their role. 
Multiple stakeholders are supported within the same system environment, including system 
administrators, registration officers, test officers, license issuers, institute managers, and institute 
trainers. Although these users share the same desktop application, the user interface and available 
menus are dynamically adjusted based on the authenticated user’s role. This approach avoids 
duplication of applications, simplifies deployment, and improves system maintainability. 
The system also integrates driving institutes as part of the license issuance workflow. Training is 
modeled as a mandatory stage within the new driving license application process, rather than as a 
separate application type. Applicants select an institute and training batch using the mobile 
application, while institute staff manage batches, training progress, and attendance through the 
desktop application. Completion of training is a prerequisite for enabling driving test scheduling 
by DVLD officers. 
External systems, such as payment services and notification mechanisms, may interact with the 
DVLD system. However, training fees are handled externally by driving institutes and are not 
processed as part of DVLD financial transactions. 93 
 
Overall, the system design emphasizes security, scalability, role separation, and real -world 
alignment, providing a clear and practical blueprint for implementation while supporting efficient 
coordination between DVLD authorities, driving institutes, and applicants. 
4.2. Purpose of the System Design 
The purpose of the system design for the Driving License Management System (DVLD) is to 
translate the identified functional and non -functional requirements into a structured, 
implementable, and maintainable solution. This design serves as a blueprint that guides system 
development, integration, testing, and future enhancement. 
The system design aims to ensure that all functional requirements such as license application 
processing, mandatory training management, test scheduling, license issuance, and renewal are 
supported in a clear and logical workflow. By integrating driving institute training as a mandatory 
stage within the new driving license application process, the design ensures real -world accuracy 
and enforces regulatory compliance before applicants proceed to driving tests. 
From a non-functional perspective, the design focuses on security, scalability, maintainability, and 
usability. The use of role -based access control (RBAC) ensures that users can access only the 
system functions relevant to their responsibilities, thereby protecting sensitive data and reducing 
the risk of unauthorized actions. A single desktop application with dynamic role -based interfaces 
minimizes system complexity and simplifies deployment and maintenance. 
The system design also supports the system model and object -oriented model by clearly defining 
system components, subsystems, classes, and their interactions. Business logic is separated from 
the presentation to promote modularity and reduce coupling, maki ng the system easier to test, 
debug, and extend. New features, such as training management, can be added without affecting 
core licensing and testing logic. 
Finally, the system design facilitates effective implementation and testing by providing well -
defined interfaces, workflows, and data structures. This structured approach ensures that each 
subsystem can be developed and verified independently while maintai ning seamless integration 
across the entire DVLD system. 94 
 
4.3. Design Goals 
The design of the Driving License Management System (DVLD) is guided by a set of well-defined 
design goals and object -oriented principles to ensure that the system is robust, scalable, secure, 
and easy to maintain. These goals influence architectural decisions, subsystem decomposition, and 
implementation strategies. 
Modularity is a primary design goal of the DVLD system. The system is divided into distinct 
subsystems such as user management, license applications, training management, testing, and 
license issuance. Each subsystem performs a specific function, allowing independent 
development, testing, and maintenance without affecting other parts of the system. 
High cohesion and low coupling are emphasized throughout the design. Components within a 
subsystem are closely related and focused on a single responsibility, while dependencies between 
subsystems are minimized. For example, training management logic is isolated from licensing and 
testing logic, ensuring that changes in training processes do not impact core DVLD operations. 
Abstraction and encapsulation are applied to hide internal implementation details and expose only 
necessary interfaces. Business rules, validation logic, and data access operations are encapsulated 
within the business layer, preventing direct access from t he presentation layer. This improves 
system security and reduces complexity. 
The system design also follows object -oriented principles such as inheritance and polymorphism 
where appropriate. Common attributes and behaviors are abstracted into base classes, enabling 
code reuse and extensibility. Polymorphism allows the system to han dle different user roles and 
processes using unified interfaces while executing role-specific behavior. 
Reusability and scalability are key design goals. Avoiding duplicated applications and adopting a 
single role-based desktop application allows shared components to be reused across multiple user 
roles. The architecture supports future expansion, such as adding new roles, services, or modules, 
with minimal changes to existing components. 
Finally, security and usability are central to the system design. Role-based access control ensures 
secure operation, while dynamic user interfaces tailored to each role improve usability and reduce 95 
 
user errors. Together, these design goals ensure that the DVLD system is efficient, reliable, and 
aligned with real-world operational requirements. 
4.4. Proposed System Architecture 
The proposed architecture of the Driving License Management System (DVLD) is based on a 
layered architectural style, which separates the system into clearly defined layers to improve 
maintainability, scalability, and security. This architecture ensures tha t responsibilities are well 
organized and that changes in one layer have minimal impact on others. 
The presentation layer is responsible for user interaction and includes two main interfaces: a 
desktop application and a mobile application. The desktop application is used by DVLD staff and 
driving institute personnel and operates as a single executable w ith role -based access control 
(RBAC). Based on the authenticated user’s role, the system dynamically loads the appropriate 
menus and screens. The mobile application is designed for applicants and allows them to apply for 
licenses, select driving institutes and training batches, and track training and application status. 
The business logic layer contains the core system functionality and enforces all business rules. It 
handles processes such as license application management, training coordination, test scheduling, 
result evaluation, and license issuance. Training -related services are implemented as separate 
business components and are integrated into the new driving license application workflow without 
interfering with licensing or testing logic. This layer acts as an intermediary between the 
presentation and data layers, ensuring consistency and validation of system operations. 
The data access layer manages persistent data storage and retrieval. It provides controlled access 
to the database and ensures data integrity through well-defined data models and relationships. Core 
entities such as applicants, applications, licenses, test s, training batches, and attendance records 
are stored in the database, with training data logically linked to license applications. 
The DVLD system architecture also supports interaction with external services, such as payment 
gateways and notification systems. While DVLD -related payments are processed within the 
system, training fees are managed externally by driving institutes and ar e not handled as part of 
DVLD financial transactions. 96 
 
Overall, this layered architecture promotes separation of concerns, enhances system security, 
supports role-based operations, and provides a flexible foundation for future enhancements to the 
DVLD system.

4.5. Subsystem Decomposition 
This section describes the decomposition of the Driving License Management System (DVLD) 
into well -defined subsystems based on functional responsibilities. The objective of this 
decomposition is to group related system components and modules into logical s ubsystems that 
simplify system design, development, testing, and maintenance. 
The DVLD system is decomposed using a functional and hierarchical approach, where each 
subsystem represents a major operational domain of the system. Each subsystem is designed to be 
highly cohesive, performing a specific set of related functions, while ma intaining low coupling 
with other subsystems through clearly defined interfaces. 
Based on the proposed system architecture and functional requirements, the DVLD system is 
decomposed into the following primary subsystems: 
1. User and Access Management Subsystem 
This subsystem groups all components related to user authentication, authorization, and 
role-based access control. It manages system users, roles, and permissions for DVLD 
staff and driving institute personnel, ensuring secure and controlled access to system 
functionalities. 
2. License Application Management Subsystem 
This subsystem is responsible for creating, processing, and tracking driving license 
applications. It manages application types such as new driving license applications, 
renewal requests, replacement requests for lost or damaged licenses, and international 
license applications. It acts as the central workflow coordinator and interacts with 
training, testing, and license-related subsystems. 
3. Training Management Subsystem 
This subsystem groups components related to driving institute operations, including 
institute management, training batch creation, applicant enrollment, attendance tracking, 
and training completion verification. Training is modeled as a mandatory stage for new 
driving license applications and must be completed before applicants can proceed to 
testing. 98 
 
4. Testing Management Subsystem 
This subsystem manages all driving test-related activities, including test scheduling, test 
execution, result recording, and eligibility verification. It also supports test retake 
management, allowing applicants who fail a test to reschedule and retake the required 
tests according to DVLD regulations. 
5. License Issuance Subsystem 
This subsystem includes components responsible for issuing new driving licenses and 
international driving licenses after applicants successfully complete all required stages. It 
generates license records and maintains license issuance history. 
6. License Renewal and Replacement Subsystem 
This subsystem manages license renewal processes and handles replacement of lost or 
damaged licenses. It verifies eligibility, validates required conditions, and updates license 
status without repeating unnecessary application stages. 
7. Payment and Notification Subsystem 
This subsystem groups components responsible for managing DVLD-related payment 
records associated with system services such as license applications, test fees, renewals, 
and license replacements. Payments are recorded and maintained internally within the 
system database, where each payment is directly linked to the corresponding process or 
entity that requires payment. The subsystem does not integrate with external banking or 
payment gateway systems in the current implementation.

4.10. Access Control 
The Driving License Management System (DVLD)  incorporates robust access control 
mechanisms to safeguard system security, protect sensitive data, and ensure proper authorization 
of users. Access control is a fundamental aspect of the system’s architecture, designed to restrict 
functionalities based on user identity and assigned responsibilities. By enforcing strict boundaries 
between roles and permissions, the DVLD system minimizes risks of unauthorized actions and 
ensures that each user interacts only with the features necessary for their duties. 
At the core of this design is Role-Based Access Control (RBAC), the primary mechanism used 
to manage permissions. Under RBAC, every system user is assigned a specific role, and 
permissions are granted according to that role. This structured approach guarantees that staff, 
institute personnel, and applicants operate within clearly defined boundaries, reducing complexity 
while maintaining flexibility. 
User Roles and Permissions 
The DVLD system supports multiple user roles, each with predefined permissions tailored to their 
responsibilities: 
● System Administrator – Oversees the entire system, manages user accounts, configures 
permissions, and ensures smooth operation of all modules. 
● Registration Officer – Handles applicant registration, manages submitted applications, 
and verifies applicant details. 
● Test Officer – Schedules and supervises vision, theory, and practical tests, records results, 
and manages retakes. 
● License Issuer  – Responsible for issuing new licenses, renewals, replacements, and 
handling detained or revoked licenses. 
● Institute Manager – Manages driving institutes, training batches, and ensures compliance 
with DVLD standards. 
● Institute Trainer – Tracks applicant attendance, supervises training sessions, and records 
progress during the training phase. 113 
 
● Applicant – Accesses limited functions through the mobile application, such as submitting 
applications, booking test appointments, and viewing license or application status. 
This role-based structure ensures that DVLD staff can manage applications, tests, and licenses, 
while institute staff focus exclusively on training -related activities. Applicants, meanwhile, are 
restricted to self-service features, preventing them from accessing administrative or sensitive data. 
Authentication and Authorization 
Access control begins with authentication, which is carried out through a secure login mechanism 
designed to verify user credentials before granting access to the system. This process ensures that 
only legitimate users are able to enter, protecting sensiti ve data and preventing unauthorized 
activities. By enforcing strong authentication measures, the system maintains integrity, safeguards 
user information, and establishes a trusted foundation for all subsequent operations. 
Once authenticated, authorization checks are applied to determine which menus, screens, and 
operations are available to the user. The system dynamically loads user interfaces based on the 
authenticated user’s role, ensuring that restricted features remain inaccessible. For example, a Test 
Officer will see test scheduling and result management options, while an Applicant will only see 
application submission and status tracking features. This dynamic interface design enhances 
usability while reinforcing security. 
Data Access Control 
Beyond functional restrictions, the DVLD system enforces strict and role-based data access control 
to safeguard sensitive information. Critical data such as license details and applicant records are 
accessible only to authorized DVLD staff whose responsibi lities require direct interaction with 
these records. In contrast, institute trainers are limited to training -related information, ensuring 
they have the resources necessary for their duties without exposure to confidential applicant data. 
This separation of access not only protects privacy but also strengthens accountability, reduces the 
risk of misuse, and maintains the integrity of the overall system. 
To further strengthen security, the DVLD system prohibits any direct access to the database from 
the presentation layer, ensuring that user-facing components cannot bypass established safeguards. 114 
 
Instead, all data operations are routed exclusively through the business layer, which enforces strict 
access rules, applies business constraints, and validates requests before they reach the database. 
This layered architecture not only prevents unauthorize d queries but also guarantees consistency 
across transactions, reduces the risk of data misuse, and provides a clear separation of 
responsibilities between system components, thereby enhancing both reliability and 
maintainability. 
Security and Future Enhancements 
The access control design significantly enhances overall system security by minimizing 
unauthorized actions and reducing the likelihood of data breaches. By carefully aligning user 
permissions with specific roles and responsibilities, the DVLD system ensures that each actor has 
access only to the information and functions necessary for their tasks. This role -based approach 
not only strengthens accountability and transparency across all operations but also helps maintain 
data integrity, protect sensitive rec ords, and build trust among stakeholders who rely on the 
system’s reliability and security. 
The architecture is also forward‑looking, allowing for future enhancements  without major 
structural changes. Potential improvements include: 
● More granular permission levels for fine‑tuned control. 
● Comprehensive auditing of user activities to track and analyze system usage. 
● Integration with external authentication services such as biometric verification or single 
sign‑on (SSO). 
These enhancements would further strengthen the system’s resilience by ensuring it can withstand 
potential disruptions and continue operating reliably under varying conditions. At the same time, 
they preserve the system’s scalability, allowing it to handle growing numbers of users, institutions, 
and services without performance degradation. By maintaining adaptability, the system remains 
flexible enough to integrate new features, support evolving requirements, and align with future 
expansion goals, ultimately providing a secure and sustainable foundation for long-term success.

5.5.2 Server-Side Implementation 
The server-side of the Driving and Vehicle License Department (DVLD) Management System is 
designed using a layered and service-oriented architecture that supports both desktop and mobile 
clients. The system separates presentation concerns from business log ic and data access 
responsibilities, ensuring high maintainability, security, and scalability. 
The DVLD system operates as a multi-client platform, consisting of: 
● A Windows Forms desktop application for DVLD staff and driving institutes 
● A mobile application for applicants 
Both clients interact with a centralized backend through shared business logic and secure data 
access mechanisms, with the mobile application communicating via ASP.NET Core Web API 
services. 
5.5.2.1 Server Architecture 
The DVLD system follows a layered architecture with service exposure, enabling multiple client 
platforms to operate on the same core system logic. 
Main Architectural Components 
1. Presentation Layer (PL) 
The Presentation Layer consists of two active client applications, each serving a specific user 
group. 129 
 
a) Desktop Presentation Layer (Windows Forms) 
Function: 
Provides a rich desktop interface for DVLD staff and driving institute personnel. 
Responsibilities: 
● Capture user input through forms and controls 
● Display structured data and reports 
● Perform UI-level validation 
● Restrict access based on user roles 
● Forward requests to the Business Logic Layer through direct method calls 
b) Mobile Presentation Layer (Applicant Mobile Application) 
Function: 
 Provides applicants with mobile access to DVLD services. 
Responsibilities: 
● Allow applicants to submit and track applications 
● Display test schedules and license status 
● Receive system notifications 
● Communicate exclusively with the backend via RESTful APIs 
● Send and receive data in JSON format 
The mobile client does not access the database directly and relies entirely on the Web API for 
secure communication. 
2. Service Layer (ASP.NET Core Web API) 
Function: 
Acts as a secure communication bridge between the mobile application and the core DVLD 
system. 
Responsibilities: 130 
 
● Expose DVLD functionalities through RESTful endpoints Authenticate and authorize 
mobile users 
● Validate incoming HTTP requests 
● Invoke Business Logic Layer methods Return structured JSON responses 
● Enforce security policies and access rules 
Key Characteristics: 
● Built using ASP.NET Core Web API 
● Stateless request handling 
● Platform-independent client support 
● Reuses existing .NET business logic libraries 
3. Business Logic Layer (BLL) 
Function: 
 Represents the core processing engine of the DVLD system and is shared across all client 
platforms. 
Responsibilities: 
● Enforce DVLD business rules and workflows 
● Validate system operations (eligibility, test requirements, license issuance) 
● Coordinate multi-step processes 
● Apply role-based permissions 
● Serve both desktop and API requests using the same logic 
Implementation Detail: 
 The BLL is implemented as a .NET Framework C# class library, allowing it to be: 
● Directly referenced by the desktop application 
● Consumed by the ASP.NET Core Web API 
4. Data Access Layer (DAL) 131 
 
Function: 
 Handles all interactions with the Microsoft SQL Server database. 
Responsibilities:

Implementation Detail:  
The DAL is implemented as a .NET Framework C# class library, ensuring consistent and secure

Architectural Advantages
